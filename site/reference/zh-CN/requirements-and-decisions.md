# Rivomesh 需求、决策与实现边界

更新日期：2026-11-16。English: [Requirements and decisions](/reference/en/requirements-and-decisions.html)。

本文记录产品范围与实现状态。**已确认需求不等于当前版本已经支持**；运行方式以 [README](https://github.com/rivomesh/rivomesh/blob/main/README.md) 为准。平台设计、目标能力和场景扩展见[平台设计](/reference/zh-CN/platform-design.html)。

平台边界为：**任务单源，平台多任务**。不做隐式跨源合表或跨源事务。多份配置可由同一控制台管理、由隔离的 worker 执行，也可部署多份服务。

`source.nodes` 仍只表示同一复制拓扑的候选地址。任务标识、状态命名空间、资源配额及复制客户端 serverId 必须隔离；重叠目标表默认拒绝。

## 多库与多目标

下例保留为产品逻辑映射；实际可运行配置见 [V3 运行手册](/reference/zh-CN/pipeline-v3.html) 和 `config/pipeline-v3.yml`：

| 任务 | MySQL database | 目标实例 | 目标命名空间 |
|---|---|---|---|
| sales | orders | gauss-a | app / orders |
| sales | crm | gauss-a | app / crm |
| sales | orders | doris-b | analytics / orders |
| legacy | finance | dm-c | 按产品命名规则显式指定 |

映射需版本化并检查大小写、保留字、名称截断及冲突。新订阅单独建立基线，不能直接复用其他订阅的游标。不同独立配置默认分别采集；只有源身份、过滤范围和安全/存储策略一致且显式关联时，才允许共享采集流，不能偷偷合并任务。

一个 v3 任务内共享有序源日志，再按映射分发，各目标独立保存全量游标、投递/应用/可见位置与错误。一个目标 SQL 错误不应暂停其他目标；公共采集解析错误可能影响该任务全部目标。

同一源事务在支持该原子边界的关系型目标内整体提交。不同实例间不引入跨目标 XA；Doris 可用的单/多表事务按版本探测，ClickHouse/Hive 使用对应的批次/物化协议，不能假装全部目标都有跨表原子提交。目标不满足任务要求时预检查阻止启动，或由用户显式选择界面已说明的较弱一致性模式。

## 故障恢复与日志存储

保留关系型目标“业务数据与本目标断点原子提交”和 owner 隔离。非同事务断点的目标需要可重试批次、目标提交确认、去重/版本策略和可见水位，不能以提前推进外部断点代替。

| 模式 | 无额外独立存储 | 故障边界 |
|---|---|---|
| 本地持久日志 | 是；使用本机持久目录或持久卷 | 进程重启恢复；磁盘永久丢失不保证无损；跨节点接管需要可访问原日志及可靠隔离 |
| 复用目标库日志 | 是；仅适用具备所需事务/状态能力的目标 | 复用目标故障可能阻塞采集；不能把任意分析库当作现有 Gauss 管理表后端 |
| 独立共享日志 | 否；使用明确支持的 HA 存储适配器 | 允许 worker 跨节点接管；仍受日志存储本身可用性和容量约束 |

日志持久化必须先于采集 GTID 推进；回收依据所有有效订阅者的持久化安全进度及基线依赖。慢目标达到配额时告警和背压，不静默删未消费数据。独立任务在资源池内也要有配额，避免单个离线目标耗尽整个平台。

切主需校验采集及所有相关全量读取依赖 GTID。源永久丢失的事务不能由 CDC 重建；事务/日志缺口不能靠编辑 GTID 跳过。分布式元数据需要兼容的分布键/唯一约束和持久化源流序号，不能按多 CN 自增 ID、时间戳或 GTID 字符串排序。

## 兼容和索引策略

“尽量都支持”落实为能力探测及兼容矩阵，包含产品、版本、模式、引擎、驱动、对象和一致性等级；状态区分已验证、实验、未验证和不支持。不能将 JDBC 连通等同于同步可用，也不能把某个最新版本的功能泛化到所有旧版本。

其他目标的业务次级 UNIQUE 若存在实际兼容问题，可以降级为普通索引或该产品等效访问结构，并保存差异清单；产品根本不存在等价索引时明确报告，不能伪造索引。无主键表的候选唯一定位键、内部技术键以及 Doris/ClickHouse 的行物化键不属于可任意降级的业务次级约束。详见 [Gauss 索引策略](/reference/zh-CN/gaussdb-index-policy.html) 和[平台设计](/reference/zh-CN/platform-design.html)。

## 不再作为阻塞问题的事项

用户已经明确产品广覆盖、硬件性能标准、存储可选、无主键/JSON/生成列、既有目标尽量支持、其他目标按需降级 UNIQUE、Rivomesh 命名、多配置多任务和 Web 界面。不会再重复询问是否需要这些能力。

具体环境接入时由向导采集真实版本、模式、schema、数据量及权限，自动生成适配和容量报告；不要求现在预先列完所有未来客户环境。业务规则、目标已有数据的冲突优先级、危险对象变更及正式切换仍必须针对实际任务明确选择，不能由“尽量支持”推导成任意覆盖/删除数据。

DDL 仍需按操作和目标能力分类：新增、兼容修改、破坏性修改、生成表达式变化与分区变化，分别提供自动执行、需要迁移计划和阻止执行的结果。首版纳入上述三类源对象不表示所有 MySQL 表引擎、SQL 函数和 DDL 自动兼容。

## 交付与验收

实施顺序建议：品牌更名 → 能力模型及任务隔离 → 行身份/JSON/生成列/DDL → 可选日志与多目标适配 → UI 恢复与校验 → 切换接管 → 全平台基准和交付矩阵。UI 应随核心操作逐步交付，不能等所有适配器完成后才补界面。

测试需覆盖多任务隔离、跨库事务、目标独立恢复、日志回收/背压、无键重复行计数、生成表达式历史版本、JSON 精度、既有目标差异、分析目标重试可见性、源切换和旧 owner。[验证记录](/reference/validation.html) 分别列出 v2 HA、v3 三目标/双日志、HTTP/DOM 和消息 Broker 实测；重复回归数量不相加冒充不同用例。剩余能力仍须专项验收。

## FAQ

**多份配置能否配置多个独立 MySQL？** 可以。Web 平台已加载多份独立配置、托管独立 Worker；每份任务独立断点。CLI 仍可单独运行。详细限制见[控制台手册](/reference/zh-CN/console-and-deployment.html)。

**多个环境同时服务是否意味着同表双写？** 不等于。可先做单写多读、影子验证或按业务域明确写入归属。同表双方独立写需要额外的来源采集、冲突处理、防回环及应用路由，当前单向 MySQL CDC 不具备此能力。

**目标都支持后，能否都用同一份建表/写入 SQL？** 不能。公共事件模型复用，类型、索引、事务、批次提交和读取语义由目标适配器决定。

**当前可以直接启用所有新能力吗？** 不能。更名、v3 多库多目标、无主键/JSON/受支持生成列、可选日志、Web 和 Kafka/RabbitMQ/NATS/Redis Streams/Pulsar/RocketMQ 已落地。完整 DDL、其他适配器、权限/修复和业务切换仍在开发，按实现状态和验证矩阵启用。
