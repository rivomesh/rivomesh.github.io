# 管理界面数据修复

首版已通过 LOCAL/H2、外部 MySQL/PostgreSQL/openGauss 日志下的真实 HTTP/Worker/数据库验收，业务目标为 MySQL8.4/PostgreSQL17，详见[验收证据](/docs/zh/start/verification.html)。完整厂商、集群、容量及安全验收仍未完成。

## 操作顺序

1. 对 V3 任务完成“数据校验”，保留任务暂停状态，打开有差异的报告。
2. 显式勾选需要修复的目标/表，点击“生成修复计划”。首版仅开放 MySQL/PostgreSQL；最多选择200张有差异的表。不会默认勾选全部目标。
3. 在修复作业记录点击“审阅修复计划”，核对目标、表、缺失/多余/变更数量、创建人和资源预算。勾选确认后，点击“确认执行 / 重试修复”。界面提交刚读取的精确计划摘要，不使用浏览器自行计算的修复内容。
4. 查看执行结果及各目标表的提交凭据。失败或取消后，可以重新审阅同一计划并重试；先前已提交的表通过凭据识别，不重复写入。
5. 全部确认后再显式恢复同步，必要时生成新的校验报告。修复不会自动恢复，不会把历史差异报告改成 MATCH，也不代表业务接管已经获准。

只读用户和操作员不能生成、读取审阅、执行或取消修复计划。服务端通过当前认证管理员取得操作人；请求不能自行声明另一位操作人。任务配置版本、任务修订号、请求 ID、计划内容摘要及报告/目标物理检查点共同约束执行。

## 作业持久化、取消与恢复

接受生成计划请求时，服务先持久保存报告、显式选表范围和预定计划 UUID，再由独立的有界维护队列执行。重开控制器时，PENDING 作业使用相同身份；若计划文件已提交而操作记录尚未完成，则加载原计划并检查原创建人、时间和范围。异步修复不占据普通任务控制线程，但每个任务同一时间只接受一个待处理操作。

取消请求先持久化，再中断执行线程。检查点等待、依赖检查、目标扫描和 DML 的连接会检测中断；还未提交的当前表回滚。取消可能赶不上刚完成的提交，**已提交的表不会回滚**；作业显示取消也不能推断“没有改过数据”。重新审阅同一计划并重试，依据目标原生凭据确认结果。

执行完成记录保留每张表的删除/插入数、原始同步检查点及此前是否已提交。认证管理员、请求摘要和计划摘要写入控制器操作审计；业务原始行值不进入操作或审计。CLI 的操作人声明仍依赖主机信任，与此处 Web 认证不同。

控制器数据目录同时保存操作、计划和源行报告。外部日志库不能替代这份数据。Docker 挂载、Linux 持久目录、K8s PVC/备份必须包含该目录；单份本地磁盘丢失、共享 PVC 多控制器并发和真实 K8s 节点故障仍需单独验收。恢复旧报告、配置、元数据时不要绕过身份或摘要检查。

## 自动拒绝的依赖

首版不规划触发器或外键执行顺序。生成计划及每张表写入前都再次检查依赖，并拒绝带传入/传出外键、触发器的目标。PostgreSQL 还拒绝行级安全策略、分区/继承和额外写入规则，持有表锁完成相关检查。不会自动删除或禁用这些对象。

MySQL 的触发器查询需要 `TRIGGER` 权限，权限不足时空结果不等于“没有触发器”，见[MySQL 8.4 官方说明](https://dev.mysql.com/doc/refman/8.4/en/information-schema-triggers-table.html)。首版采取保守策略：要求当前账号具有**直接授予的全局 SELECT 和 TRIGGER**，并拒绝检测到部分权限撤回的配置。仅通过角色、库级/表级授予等更细粒度组合尚未解析，可能被拒绝为 `REPAIR_METADATA_VISIBILITY_REQUIRED`。不要通过移除权限检查解决此错误；应按组织权限政策选择经审阅的迁移账号，或等待相应权限配置验收。

目标表仍只允许同步服务写入；并发外部写入或任意 DDL 不在当前写入合同内。数据根变化返回 `REPAIR_TARGET_DRIFTED`，需重新校验与规划。这里检查的是已知依赖，不能据此声称覆盖任意存储过程、其他厂商模式和复杂迁移依赖。

## API

所有请求使用现有认证、`X-Request-ID` 与当前任务 `expectedRevision`：

```json
{"action":"REPAIR_PLAN","expectedRevision":"TASK_REVISION","repair":{"reportId":"REPORT_UUID","scope":["target/TABLE_ID"]}}
```

向 `POST /api/tasks/TASK_ID/actions` 提交后，202响应中的 `operations[].repair.planId` 已持久化。等待 `REPAIR_PLAN_READY`，通过 `GET /api/tasks/TASK_ID/validations/REPORT_UUID/repairs/PLAN_UUID` 读取审阅投影；它包含计数和预算，不提供原始行或当前可执行性保证。

```json
{"action":"REPAIR_EXECUTE","expectedRevision":"CURRENT_TASK_REVISION","repair":{"reportId":"REPORT_UUID","planId":"PLAN_UUID","approvedHash":"EXACT_PLAN_SHA256"}}
```

执行要求控制器期望状态 PAUSED；运行中的任务须先完成校验并暂停。取消使用 `REPAIR_CANCEL`，不附带 repair 输入。请求重放沿用原始请求 ID、正文、修订号及身份；不同请求 ID 配合过期修订号会被拒绝，不会再创建作业。

## FAQ 与仍待完成

- **计划已生成，为什么执行失败？** 数据、结构、配置或暂停状态可以在审阅后变化，执行必须重新检查。计划不是永久有效的写入许可。
- **错误摘要或旧版本页面会写入吗？** 摘要不匹配在执行器中拒绝；旧修订号在接受作业前拒绝。
- **取消后显示失败，如何判断哪些表提交了？** 使用同一计划重试，凭据会解析已提交表。完整实时逐表进度目录、独立凭据浏览和报告保留/清理仍待补齐。
- **SQL 错误导致目标尚未追平，能直接修复吗？** 当前为共同校验点修复。失败事务可以按对应条件使用[前镜像补偿](/docs/zh/reference/transaction-compensation.html)或[审阅跳过](/docs/zh/reference/transaction-skip.html)。非空接管、约束恢复和业务切换仍待实现。
- **预算可以在界面修改吗？** 首版计划沿用 CLI 默认预算，显示供审阅；界面编辑修复预算尚未开放。完整厂商/版本/集群/容量、安全和控制器 HA 矩阵仍未完成。
