# Gauss 目标的索引转换、正确性与业务接管

更新日期：2026-11-14。English: [Gauss index policy](/docs/en/reference/gaussdb-index-policy.html)。范围及待确认事项见[需求与决策](/docs/zh/reference/requirements-and-decisions.html)。

**状态：v3 已实现普通次级索引及业务 UNIQUE 降级，v2 仍仅建字段/主键。** `IndexPolicy` 生成明确转换动作，`JdbcSink` 在新建表时执行支持的普通索引；表达式/前缀/倒序/特殊方法及既有 UNIQUE/GSI 要求单独计划，不自动 DROP。业务 GSI 模型可转普通索引，身份 GSI 不降级；商业分布式 GaussDB 仍待实机验收。操作与边界见 [V3 手册](/docs/zh/reference/pipeline-v3.html)。

## 已确认的同步策略

MySQL 是数据权威源。同步期间目标仅由同步服务写入，业务应用可以只读；应用接管写入前必须完成数据校验并恢复必要约束。对 Gauss 的新建业务表：

| 源对象 / 目标需求 | 同步阶段策略 |
|---|---|
| MySQL PRIMARY KEY | 保留稳定行身份及唯一性，不降级为普通索引 |
| 业务次级 UNIQUE(email) 或联合 UNIQUE | 转成对应列及顺序的非唯一普通索引；保留可兼容的列定义及 NOT NULL |
| 普通二级索引 | 按目标能力创建普通索引 |
| 为次级 UNIQUE 或查询加速而计划引入的 GSI | 改用普通二级索引，不保留全局路由/唯一约束能力 |
| 为主键、行身份或内部正确性必需的唯一结构 | 不适用降级规则；选择兼容的分布/约束方案，否则预检查失败 |
| 同步管理表的事务去重、owner/租约、断点唯一约束 | 必须保留，不能按业务索引规则弱化 |
| 已有目标 UNIQUE、GSI、外键依赖等 | 检查依赖并生成差异/迁移计划；不自动 DROP 或原地弱化 |

普通索引不能代替主键。不能把原来的全局 UNIQUE 擅自改成 `UNIQUE(email, distribution_key)` 并宣称等价：这允许不同分布键下重复 email，且仍然保留同步过程中可能不需要的约束。

本专题适用于 openGauss/分布式 GaussDB。其他目标在约束不兼容时也已允许降级业务次级 UNIQUE，具体方式由各适配器声明；主键/候选定位键和内部正确性约束不能降级。分析引擎的 Unique Key/物化键也不属于可任意降级的次级约束，详见[平台设计](/docs/zh/reference/platform-design.html)。

## UNIQUE(email) 的含义

源表示意：

```sql
-- MySQL
CREATE TABLE customer (
    id BIGINT NOT NULL,
    email VARCHAR(64),
    PRIMARY KEY (id),
    UNIQUE KEY uk_customer_email (email)
);
```

目标逻辑示意，非当前程序自动产物，也不是所有版本通用脚本：

```sql
-- 按目标能力选择具体类型/长度、分布及索引方法
CREATE TABLE app.customer (
    id BIGINT NOT NULL,
    email VARCHAR(256),
    PRIMARY KEY (id)
);
CREATE INDEX ix_customer_email ON app.customer (email);
-- 分布式 GaussDB 还需按能力规划表分布，例如 HASH(id)。
-- 上述长度遵循当前项目 UTF-8 字节扩容策略，不能替代实际版本检查。
```

不创建目标 UNIQUE 不会主动制造重复；数据最终是否正确，依赖源到目标的完整复制。对于已追平的同一个源事务边界，只要满足以下条件，目标应保留源中每个主键对应的同一行：

1. 源事务全部有 binlog，采集完整，FULL 行镜像、事务顺序和映射均正确。
2. 主键映射保持一一对应，目标主键比较语义不合并不同源键。
3. 全量与增量衔接无遗漏，重复投递被持久化 GTID/断点和幂等应用处理。
4. 业务修改与应用断点原子提交，重试不跳过失败事务，旧 owner 被隔离。
5. 没有额外写入、触发器副作用、丢失精度的转换或两个源表合并写入。

满足这些条件时，源端负责约束 email，目标负责复制结果。**目标普通索引本身不再检查 email 唯一性。** 重试幂等依靠主键和事务断点，不能依靠 email 索引，也不能把“无目标 UNIQUE”当成故障恢复方案。

源允许的多个 NULL 需要如实复制；对 NULL 的约束语义不能简单套用 `GROUP BY email HAVING COUNT(*) > 1`。大小写、排序规则、尾随空格、空字符串/NULL 及类型转换可能使目标的相等判断不同于 MySQL。因此“源端唯一”不等于“目标未来建立同名 UNIQUE 必定成功”。

## 全量阶段可能出现临时重复值

现有全量是在线分块扫描加日志回放，并非全库同一时间点快照。例如：扫描到 `id=1,email=a` 后，源事务把该行改为 b 并插入 `id=2,email=a`；随后扫描到 id=2。追平之前，目标可能暂时有两个不同主键都为 email=a；源在每个已提交状态都合法。

这类临时次级键重复不等于主键行重复，不能据此丢弃数据。完整有序回放后应恢复到源边界的正确结果。全量/早期追平结果不得作为一致性数据对外承诺；需要一致读取的消费者等待指定屏障并按约定读取。

普通次级索引允许这种过程状态，也是本策略适合当前在线扫描方式的原因之一。即使以后选择保留某些目标 UNIQUE，也必须重新设计快照/回放与约束建立时机，不能只在建表 SQL 中加入 UNIQUE。

## GSI 是否能改普通索引

可以在**新建表的索引规划**中选择普通索引，以保留对应列的基本访问路径；这属于有明确能力变化的替代，不是数据库原生无损“转换”。MySQL 源没有 Gauss GSI，不能通过替换 MySQL DDL 中的关键字来实现。

华为的分布式 GaussDB 文档说明 GSI 可以拥有与基表不同的分布；其调优示例展示，同一非分布列条件使用普通索引时访问所有 DN，使用 GSI 时可以定位单个 DN。因此本方案接受可能增加跨节点查询开销，不承诺相同性能。具体限制必须以实际版本为准。[CREATE GLOBAL INDEX](https://support.huaweicloud.com/intl/zh-cn/distributed-devg-v8-gaussdb/gaussdb-12-0546.html)、[官方查询计划示例](https://support.huaweicloud.com/intl/zh-cn/distributed-devg-v8-gaussdb/gaussdb-12-1729.html)。

对项目的设计影响：

- 普通索引不提供跨 DN 的全局唯一性，也不保留 GSI 独立分布/覆盖列设计；替换索引不会改变基表分布。
- 保留索引列不表示查询计划、覆盖查询或 JOIN 性能等价，需要真实查询与 `EXPLAIN` 验证。
- 主键若只能依赖某种全局唯一结构才能正确成立，不能把它降级。优先规划与主键相容的分布键；无法满足则拒绝建表并报告原因。
- 现存 GSI 可能承载约束或其他依赖，迁移要识别索引所有权、依赖、有效状态和回滚路径，不能盲目 DROP。

注意：分区表的 GLOBAL/LOCAL 索引表示索引覆盖分区的范围，不能与分布式 GSI 混为一谈。openGauss 的分区索引语法也不能直接当成 GaussDB GSI 能力证明。[openGauss 索引文档](https://docs.opengauss.org/zh/docs/latest/database_administration_guide/creating_and_managing_indexes.html)。

## 分布式表和管理表

普通索引策略只放宽业务次级约束，不消除分布式表对主键、分布列、分区列或数据类型的要求。分布方案要确定性、可诊断、可覆盖配置，并检查主键更新或分布键更新时的写入策略。

管理表单独设计：去重键、任务标识、流序号和租约操作必须满足分布式约束，数据与本目标断点仍须原子提交。不能为了避免 GSI，把管理表的 `UNIQUE(job_id, transaction_key)` 删除，或仅凭各 CN 的自增 ID 推断源顺序。现有管理表布局未经商业分布式 GaussDB 实测，不作为直接部署模板。

## 索引规划与可恢复执行

后续实现应包含以下过程，不能把任务简化成“去掉 UNIQUE 关键字”：

1. 发现源表及索引元数据：主键/次级、列顺序、前缀长度、表达式、排序、可见性和索引类型，生成固定版本的转换清单。
2. 根据目标产品、版本、模式、分布/分区和列类型，生成可执行 DDL 及能力差异报告。等价目标索引可去重，名称截断需带稳定摘要避免冲突。
3. 全量前创建字段和主键，保存表定义、转换策略及指纹；首先保证正确行定位。
4. 建议在首次追平后创建普通业务次级索引，限制建索引并发；已进入增量不代表索引全部 READY。数据进度和索引就绪状态分别展示。
5. 对每个目标/表/索引记录计划、开始、成功、失败和定义摘要；重启先查目录，核对定义及有效性，再继续。DDL 非事务性或在线建索引留下无效对象时，按适配器提供的恢复步骤处理。
6. 相同名字但定义不符不能当作成功；失败保留诊断并重试该对象，不回退全量游标，也不跳过业务事务。若 DDL 故障影响安全写入，暂停该目标；若仅缺查询加速索引，可让该目标继续增量但标记索引阶段失败。

前缀、表达式、FULLTEXT、SPATIAL、不可见索引、超长键及不支持的排序规则都要逐对象报告。初版建议仅自动转换普通列 B-tree 类索引；其他对象生成明确的未支持/需手工处理报告，不能静默当成“全部索引同步成功”。不自动把前缀索引扩大成整列索引，以免超长或改变计划。

## 业务接管流程

以下是计划中的操作规程，不是当前已提供的自动化命令。每个准备接管的目标独立验收，不要求全部目标同时切换：

1. 冻结源的相关业务写入及 DDL，记录最终源 GTID 屏障；确认没有双写入口。
2. 等该目标完整应用到屏障，且无失败事务、缺失日志或未完成全量；使用可证明的目标应用位置，不能只看公共采集 GTID。
3. 对同一静止边界核对行数、主键集合、分块摘要/必要逐行值，以及准备恢复约束的比较语义。索引转换清单保存原 UNIQUE 定义，作为恢复依据。
4. 按目标实际比较规则校验重复、NULL、长度及约束依赖，创建所需 UNIQUE/外键等约束。分布式版本若必须使用 GSI 或调整表分布，在本阶段单独规划并验收；同步阶段使用普通索引不代表接管阶段可以永久省略约束。
5. 必要约束全部有效、数据检查成功后，停止或隔离该目标同步写入，再允许应用写目标。检查失败则不开放写入，修复后重试；不得删掉冲突行以强行通过。

目标开始写业务数据后，不能再让原单向同步服务无协调地覆盖它。回切或双向同步属于另一套方案，不因保留了 GTID 就自动获得支持。其他仍做镜像的目标可继续保持自己的同步关系，但源业务改到新库之后，原 MySQL 源不会自动包含新业务写入。

## FAQ

**去掉 UNIQUE，重试会多插入一行吗？** 本专题的有键方案按主键和事务断点幂等处理；email 普通索引不参与去重。无主键已纳入首版需求，但当前代码仍拒绝：需实现候选键或一致基线/多重集方案，不能直接套用有键保证，详见[平台设计](/docs/zh/reference/platform-design.html)。

**多个源行 email 相同是否永远是错误？** 不是。NULL、源/目标比较语义差异以及追平前的混合扫描状态都要区分。用源定义及约定边界判断，不自动删除“重复”行。

**普通索引一定比 GSI 快吗？** 不能保证。可能减少写入维护成本，也可能增加查询访问的 DN 数；以实际工作负载验证。

**已有目标 UNIQUE 会自动变普通索引吗？** 当前不会；后续也默认先生成对象差异和依赖计划。约束拥有的索引不能直接当作独立索引删除。

**建索引中断是否重做全量？** 设计要求保留数据断点、检查索引目录后恢复索引阶段。此能力尚待实现和故障验证。

**同步阶段不保留 UNIQUE，接管能保证建成功吗？** 不能提前保证。接管必须执行实际语义校验与建约束；不支持的分布/约束或不一致的数据都应阻止接管。

## 验收清单

- 单列及联合 UNIQUE 转非唯一索引，列顺序、NULL/NOT NULL、索引清单可追踪；PK 和内部唯一约束未被弱化。
- 在线扫描中出现临时 email 重复，正常追平后与固定源边界一致；更新、删除、主键修改和事务重放不丢行。
- 多目标进度不同时分别验证结果；一个目标建索引失败不错误修改其他目标状态。
- 索引 DDL 前后杀进程、目标连接丢失、提交响应不确定、同名异定义、无效索引和旧 owner 均正确处理。
- 分布式 GaussDB 在真实多 CN/DN 环境验证分布键兼容、全局行身份、事务顺序和普通索引查询计划；openGauss 单独验证。
- 接管前验证排序规则、空字符串/NULL、目标唯一约束和冻结屏障；故意制造冲突时阻止切换并保留全部数据。

当前 [验证记录](/docs/zh/reference/validation.html) 不包含以上新增能力；不能据此标记索引转换或商业分布式 GaussDB 已通过验收。


Doris目标的业务UNIQUE/GSI转换为非唯一倒排索引，内部UNIQUE KEY只保护源行身份；不等于GaussDB普通B树，也不保留业务唯一性、排序规则或全局路由。类型、布局和接管限制见[Doris手册](/docs/zh/reference/doris-v3.html)。
