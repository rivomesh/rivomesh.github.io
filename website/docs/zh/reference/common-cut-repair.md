# 共同校验点数据修复（首批 CLI）

MySQL8.4/PostgreSQL17 的首批修复场景已通过四种真实日志模式验收，见[证据](/docs/zh/start/verification.html)。完整生产、厂商及容量验收仍未完成。管理界面已提供经认证的计划审阅、执行、取消与重试，见[管理端修复](/docs/zh/reference/managed-repair.html)。

适用条件：MySQL 源的共同校验点已完成逐行比对，报告为 COMPLETE，源数据已经密封，任务仍保持该校验点的全局 PAUSED 状态。首批执行器限定 MySQL/PostgreSQL 事务型目标；其他关系库、分析库、消息队列的修复需要单独验证。目标业务表仅由同步服务写入，修复期间继续禁止外部写入。首批验收使用同步服务自动创建且没有触发器/外键的表；执行器会拒绝检测到的触发器、传入/传出外键及 PostgreSQL 行策略、继承等依赖；MySQL 还要求可验证的元数据可见权限。完整依赖迁移规划未实现，详见管理端修复手册。

这与“目标因 SQL 错误停在旧事务，尚未追上共同校验点”是两个恢复场景。后者仍需先排除错误并重试原事务；基于失败事务前镜像的补偿、手工跳过和一致性缺口管理尚未实现。不要调整 GTID 或目标位点来绕过错误。

## 生成和确认计划

先通过管理界面或 CLI 完成逐行校验。使用该任务实际生效的 V3 配置及私有报告目录：

```sh
java -jar rivomesh.jar repair-plan config.yml /private/reports REPORT_UUID targetA/TABLE_ID,targetB/TABLE_ID operator-id
```

TABLE_ID 是报告中的表身份，不是表名。显式选择至少一张有差异的表。计划保存到 `REPORT_UUID/repair-plans/PLAN_UUID.json`，输出包含计划 ID、内容 SHA256、表结构摘要、修复前后数据根摘要、缺失/多余/变更计数、操作人声明及资源预算，不包含原始业务值。计划将配置指纹、日志世代、epoch、序号、错误版本和所选目标的物理检查点绑定到原始报告。计划文件和报告均应保持私有权限；不能编辑后继续使用旧摘要。

当前默认最多100000条差异身份、每张表1GiB磁盘探测预算、单行4MiB；持有暂停锁的写入阶段预算10分钟，报告复核与连接预检还需额外时间，不承诺整个作业在10分钟内完成。完整证书在计划中保留，计划文件上限8MiB。超大目录的精简证书、分页规划和界面预算编辑仍待实现。物理磁盘硬限额仍需文件系统/容器配额；逻辑预算不能代替它。

核对输出后，用精确摘要执行：

```sh
java -jar rivomesh.jar repair-execute config.yml /private/reports REPORT_UUID PLAN_UUID APPROVED_SHA256 operator-id REQUEST_UUID
```

REQUEST_UUID 为本次请求生成的 UUID。CLI 的身份字段由可信运维人员声明，依赖主机访问控制；它不是 Web 登录身份，也不声称提供双人审批或控制器审计。Web 修复已独立接入认证、版本检查和持久操作记录；不能直接把这个 CLI 包装为匿名接口。

## 执行与中断恢复

执行先验证报告源密封、原始行校验和、目标历史数据摘要及计划。全局暂停日志行锁阻止并发恢复/抢占；每张表使用同一目标连接持有物理检查点锁，扫描当前目标的全部行，经私有磁盘排序生成摘要。只有与报告中的修复前状态一致，才执行删除多余/变更行、插入缺失/变更行。无主键表保留原始 occurrence ID，不生成新身份，也不合并重复行。

执行后在同一事务内重新扫描，必须匹配密封源的行数和数据摘要。业务 DML 与 `rm3_sink_repair` 凭据同事务提交，目标 stream_seq、GTID/事务身份及哈希不变。凭据不存业务值，保留计划摘要、前后数据根、原始检查点、删除/插入数、操作人、请求摘要和时间。

首次执行只允许额外创建凭据表，不重建丢失的任务、表登记或所有权元数据。MySQL 的 DDL 可能隐式提交，所以业务事务开始后重新取得检查点锁；业务表及三张元数据表均要求 InnoDB。已有凭据表必须满足列和主键要求，不能通过删除元数据“修复”身份错误。

- SQL 错误、行数不符、目标变化、报告损坏、预算或超时：当前表事务回滚，任务继续暂停。处理原因后重试同一计划；如果目标数据已经变化，需要重新校验和规划。
- 提交后丢失响应、进程退出或重启：使用同一计划及摘要重试。先查目标凭据；完全匹配时返回 `alreadyApplied=true`，不会重复修改。
- 多表、多目标：逐表本地事务，可能有部分表已提交。重试从各表凭据判断进度，没有跨库原子性保证。一个后续表失败不会撤销先前已提交的表。
- 已全部提交后又恢复同步：凭据仍可查询、重试返回历史提交结果，但这不表示目标当前内容仍等于历史报告。

修复不会自动恢复同步。确认所有表凭据和修复结果后，由运维人员执行现有恢复操作，并按需要生成新的共同校验点报告。原报告作为历史证据保留，仍显示原始差异，不会被改写为 MATCH。

## FAQ 与当前限制

**可以修复已有任意业务库吗？** 当前只处理本任务已经拥有、结构符合、快照完成的目标表；非空接管、任意结构改造、触发器/外键依赖顺序和约束重建仍需独立迁移计划。

**会处理 UNIQUE 交换吗？** 同一表先删除全部多余/变更身份，再插入预期值；跨表外键、触发器副作用与其他数据库模式不能据此推断已兼容，SQL 失败会回滚当前表。

**进程强杀后临时文件如何处理？** 正常退出删除本次探测文件。SIGKILL 可能留下私有 scratch 子目录，后续执行创建新目录，不把未完成排序结果作为有效校验；完整目录清理/保留策略仍待补齐。不要在有活动修复时删除目录。

**故障恢复是否保证跨日志库和目标的分布式事务？** 没有。暂停日志锁保护控制操作，目标本地锁及原始检查点保护写入顺序，目标凭据确认本地提交。日志连接故障、网络分区和更复杂节点故障仍需持续扩展真实环境矩阵。
