# 缺口核验：共同校验点与原子记录

[English](/docs/en/sdd/design-gap-verification.html) · [任务](/docs/zh/sdd/tasks.html) · RC-08 DONE · 限定SQL档案 / bounded SQL profile

计划、管理员API/UI、跨节点审批与取消已接入，原生PG/MySQL各58项合同及103项DOM检查通过；PG/MySQL控制库各27项真实同步链路检查通过，RC-08限定SQL档案已完成。操作步骤和FAQ见[核验手册](/docs/zh/reference/gap-verification.html)。

## 审阅范围

核验计划固定一个目标、配置摘要、日志代次、源身份、共同校验点、已封存报告及源数据摘要，最多包含100条已有缺口和1000张相关表。每条缺口必须有完整事务计划与原生执行凭据；涉及表的历史 schema 版本必须与共同点一致。不同源、目标、代次、schema、坐标或不完整/存在差异的报告拒绝生成计划。计划仅包含元数据，不包含业务行值。

历史报告 MATCH 只允许形成审阅计划，不能直接消除缺口。执行时必须重新扫描目标上所有受影响表，使用有界磁盘排序计算行数和内容摘要，与封存的源数据比较；只核对行数或只核对跳过事务的行都不充分。差异、超时、原生断点变化或源暂停围栏变化都不写入核验成功记录。

## 并发与持久化

执行持有源日志任务行锁，从读取原缺口、扫描目标，到提交核验凭据始终不释放。恢复运行、Worker所有权变更以及同步服务的修复写入必须取得同一围栏。旧Worker另受目标原生epoch与共同点约束。各表不需要同时驻留内存。

本机制要求目标业务数据仅由同步服务写入；外部应用或管理员的直接写入不在此围栏内。未来手工补数据入口也必须取得同一围栏，不能绕过它。核验针对封存的历史源共同点，不宣称源当前时刻与目标相等。

源日志增加 `rm3_gap_verification_plan` 保存不可改写的审阅计划，增加 `rm3_gap_verification` 保存成功凭据，并在 `rm3_gap` 保存核验ID与凭据摘要。一次源数据库事务同时写入凭据和全部选定缺口关联；任一步失败全部回滚。保留原始SKIP计划、回执、缺口和报告，不执行目标业务DML，不修改ACK，不恢复运行。

记录状态为 `VERIFIED_AT_COMMON_CUT`，凭据包含原审阅计划、共同点、核验时间、确认人、确认原因与执行请求ID；计划的创建人与确认人分别记录。相同执行请求、计划、确认人与原因重放返回原凭据；即使任务随后恢复运行，也只返回历史结果，不重新核验。相同请求修改原因或范围拒绝；已核验缺口不能用另一个请求覆盖。重复并发请求应得到同一凭据。凭据丢失、内容变更或关联不完整必须拒绝，不能静默创建空历史。

首版直接创建所需元数据结构，不增加旧开发候选的ALTER/迁移兼容。需要升级测试环境时先核对数据和持久状态，不能只复制游标。参见[首版基线](/docs/zh/reference/first-release.html)。

## 操作与状态

`GAP_VERIFY_PLAN`持久生成计划，`GAP_VERIFY_EXECUTE`按已批准摘要执行，`GAP_VERIFY_CANCEL`通过预留的取消通道中断任务。取消结果必须读取原凭据核对；取消与提交可能竞争，不能直接显示为“已回滚”。控制和Owner审计保留原请求、计划及结果摘要；权限撤销、修订、配置/代次变化仍受现有准入检查。

`hasGaps`继续表示原始SKIP历史，`openGapCount`与`verifiedGapCount`区分未核验和已有共同点凭据的记录。统计窗口最多1001条，`gapCountLimited`时数量是下界；没有在窗口发现未核验项时，`hasOpenGaps=null`而非false。缺口分页显示OPEN/VERIFIED_AT_COMMON_CUT及凭据引用，不覆盖原SKIPPED结果。核验成功不改变ACK、业务表或运行状态。

## 尚未完成

PG/MySQL控制库跨入口闭环各27项已通过，业务核验目标为PostgreSQL17，另有MySQL8.4健康订阅；原生PG/MySQL之外的SQL、分析库和消息目标仍未扩展核验协议。失败事务补偿、类型化手工补数据及其他目标协议仍由RC-06/07/10继续追踪。

增量水位以同一日志快照计算：安全覆盖包含显式SKIP；连续未跳过前缀止于首个历史SKIP之前，核验成功也不改写它。每目标按主键索引读取第一条历史缺口，不扫描全部缺口负载。SQL提交、Broker接收、物化确认分别标注；所有用于界面显示的序号使用十进制字符串。快照完成度独立展示。
