# RC-05：失败事务原生断点核对

状态：RC-05 限定档案已验收，见[证据](/docs/zh/evidence/baseline.html)。原有 RC-02 历史证据语义不变，跳过与补偿另行追踪。

## 交付顺序

1. 在已保存的完整失败事务基础上，核对当前日志与目标原生断点，并在事务审阅界面显示结果。
2. 对已经提交但日志尚未确认的事务，提供经过权限、漂移检查和幂等保护的确认操作。
3. 将该检查作为后续跳过与补偿的强制前置条件，完成对应界面和故障验收。

## 只读核对

第一档案为事务型 PostgreSQL、MySQL 目标。生产入口从当前任务配置派生目标连接、订阅和数据库映射，核实配置指纹与日志订阅集合；只打开既有原生元数据，不建表、不 activate、不 normalize、不推进 ACK、不恢复订阅。

核对前后两次读取暂停事务，均须与签名证据中的完整观察一致，包括源位置、原始及规范化事务、流水线世代、所有者 epoch、订阅 ACK、错误版本、错误代码和故障诊断。发现变化即拒绝。只有已保存的规范化事务能够参与计算，不以重新查询源行或重新分配无主键标识代替历史内容。

自动应用与恢复核对共用 `TransactionProjection`。它保留事务边界和 BARRIER，按目标数据库映射筛选事件，并用历史表版本计算目标事务摘要。

| 原生断点 | 结果 | 含义 |
| --- | --- | --- |
| 等于日志 ACK | CHECKPOINT_NOT_ADVANCED | 原生断点未前进；不能据此断言业务行不存在或允许跳过 |
| 等于 ACK+1，事务 ID、投影摘要全部相同 | COMMITTED_UNACKNOWLEDGED | 目标已提交，日志尚未确认；不得重放补偿或当作未应用事务跳过 |
| 序号越界、事务内容不符、目标 epoch 领先 | 拒绝 | 需要排查漂移、错误目标或外部写入 |
| 目标 epoch 落后 | 标记 targetFenceRequired | 只读核对不更新 epoch；任何后续写操作必须先完成围栏 |

结果必须带证据 ID/摘要、观察时间和双方断点。它是有时间点的观察，不能作为后续操作的永久凭据。界面不把历史结果标成当前状态；旧执行节点不返回新字段时显示核对不可用。

## 人工确认的执行约束

执行时重新核对权限、配置、证据和原生断点。日志 job/subscription 锁保护恢复和所有权变动，原生目标断点锁阻止提交漂移；ACK 与持久化操作回执在同一个日志事务中提交。保持订阅暂停，产生新错误版本使旧恢复请求失效。相同操作 ID 重试返回原回执，崩溃后不得重复写业务行。

当前确认操作在原生 epoch 落后时拒绝执行，要求通过原有暂停流程完成原生围栏并保存新证据后再试。不能在日志 ACK 提交后才依赖一个尚未提交的原生 epoch 更新。ACK 确认只适用于已经验证的原生 APPLY 提交，不得伪造 SKIP。跨节点新增写操作须显式版本/能力准入，避免旧 Agent 接收未知操作。

## 针对性验收

覆盖真实业务事务提交领先 ACK、相同 ID/不同摘要、映射过滤、空投影和 BARRIER、缺失规范化内容、历史模式缺失、错误版本/epoch/config 变化、核对期间恢复、缺失元数据不重建、目标 epoch 落后只报告、输出不含行值。先做相关 H2/原生 SQL 合同与 DOM 验证；完整恢复功能交付时再跑对应端到端和兼容矩阵。

## 首个人工确认档案

要求整个流水线 PAUSED，仅目标暂停不够。先暂停任务，推进日志 epoch 并撤销旧 Worker；确认原生目标围栏，再保存新证据。执行时持有 job/subscription 与原生断点锁，要求双方围栏 epoch 相等，ACK 与操作回执原子提交，并保持双层暂停。确认操作不自动 activate；目标围栏落后时需重试现有暂停/围栏流程后重新保存证据。内部事务、HTTP/UI 与协议6准入已通过限定档案验收；操作方式见[手册](/docs/zh/reference/commit-acknowledgement.html)。
