# 备份与故障恢复

RivoMesh 使用持久日志和进度继续处理任务。恢复所依赖的资料必须一起保留，重新启动一个进程不能替代备份。

## 需要备份哪些内容

| 内容 | 用途 |
| --- | --- |
| 平台配置和任务配置 | 恢复来源、目标、映射、日志方式和访问设置 |
| 控制器数据目录 | 保存配置版本、操作、报告、修复计划等管理数据 |
| 本地或外部事务日志 | 保存已采集、尚待目标处理的事件与进度 |
| 目标业务数据与管理状态 | 保持已经写入的数据和目标确认位置相匹配 |
| 源端日志与身份 | 保留恢复位置对应的 MySQL binlog、PostgreSQL 逻辑槽及 WAL，或 Oracle 归档。 |

数据库中的数据表、队列和状态表需要协调成同一个恢复单元。不要只恢复业务表而保留另一时间点的同步状态。

## 计划停机前

1. 记录任务状态、各目标进度与积压。
2. 需要停止整条共享任务时使用共享暂停，并确认目标实际隔离结果。
3. 按部署方式备份配置、控制器目录、日志与目标数据库。
4. 确认源端日志保留窗口覆盖停机和重新追赶。记录原 GTID、槽与 LSN 或归档 SCN。

Docker 挂载目录、Linux 数据目录和 Kubernetes PVC 都应包含控制器持久数据。外部日志库不能替代校验报告与修复计划所在的控制器目录。

复制本地 H2 日志前，先停止任务并确认所有日志连接已关闭。分离部署还要保存 Agent 的原目录身份、密钥、回执及私有证据。详见[首版部署基线](../reference/first-release)和[采集恢复](../reference/capture-recovery)。

## 服务重启后

使用原配置和持久目录启动，核对任务身份、配置版本及各目标状态。明确暂停的任务不会因为重启自动绕过暂停；先处理原因，再由有权限人员恢复。

源与目标之间的连接故障可按策略重试；SQL 类型、约束和权限等问题应先处理，再恢复原事务。

## 恢复遇到拒绝时

保留现有数据与错误信息，检查是否发生配置变化、日志缺失、状态回退或源端日志保留不足。收到目标原生回执但日志确认没有完成时，先用原配置和任务身份恢复，再审阅原事务的确认状态。

备用节点、跨主机恢复及数据库切换需要满足各自的部署条件，详见[详细运行配置](../reference/pipeline-v3)与[恢复规则](../reference/recovery)。正式使用前，应在同类测试环境演练一次完整恢复。
